# 여쭈어 (Yeojju / 여JJU) 결정 로그

이 파일은 구현 중 발생한 결정과 이유를 기록한다. 이미 `MVP_FUNCTIONAL_SPEC.md`와 `ARCHITECTURE.md`에서 고정한 내용을 임의 변경하지 않는다.

## 고정 결정

### ADR-001 신규 저장소 사용

- 결정: 기존 MVP를 리팩터링하지 않고 `travelguide-v2` 신규 저장소에서 시작한다.
- 이유: 1:1 매칭 중심 모델과 화면 구조를 끌고 가지 않고, 2.5주 동안 새 핵심 흐름만 명확히 구현하기 위해서다.
- 결과: 기존 코드는 참고만 하며 복사·붙여넣기 전 반드시 현재 요구사항에 맞는지 검토한다.

### ADR-002 웹만 개발

- 결정: Next.js 반응형 웹만 개발하고 Flutter는 제외한다.
- 이유: 동일 기능을 두 클라이언트에 중복 구현하지 않고 발표 안정성에 집중한다.

### ADR-003 제주 1개 방

- 결정: 스키마는 다중 지역을 지원하지만 UI와 seed는 제주만 제공한다.
- 이유: 네트워크 효과와 핵심 가설 검증에 지역 수는 필요하지 않다.

### ADR-004 질문 스레드형 단체방

- 상태: 2026-08-01 ADR-016으로 대체됨.
- 이전 결정: 자유 메시지 타임라인이 아니라 질문 카드와 답변 스레드를 사용한다.
- 대체 이유: 실제 사용 의도는 참여자 대화가 중심인 방이며, 구조화 질문은
  대화를 방해하지 않는 별도 토픽 레이어여야 한다.

### ADR-005 인증은 상태 기반 자격

- 결정: 사용자 계정 type을 여행자/현지인으로 고정하지 않는다.
- 이유: 같은 사용자가 여행지에 따라 여행자이자 현지인이 될 수 있다.

### ADR-006 GPS 단독 인증 금지

- 결정: 현지인 GPS는 위치 신호이고, 증빙과 관리자 승인이 최종 인증이다.
- 이유: 단발 GPS만으로 거주·지역 전문성을 검증할 수 없기 때문이다.

### ADR-007 REST write, Socket broadcast

- 결정: 질문·답변·상태 변경은 REST로 저장하고 Socket.io는 변경 이벤트를 전달한다.
- 이유: 중복 비즈니스 로직을 줄이고 재연결·테스트·데이터 일관성을 단순화한다.

### ADR-008 결제 제외

- 결정: 코인·결제·리워드는 이번 MVP에서 제외한다.
- 이유: 현재 검증 대상은 결제 의향보다 실시간 도움과 신뢰 구조다.

### ADR-009 같은 도메인 배포

- 결정: Nginx가 Web, API, Socket을 같은 HTTPS 도메인으로 제공한다.
- 이유: cookie 인증, CORS, WebSocket을 단순하게 유지한다.

### ADR-010 프런트엔드와 백엔드 디렉터리 분리

- 날짜: 2026-07-30
- 상태: accepted
- 문제: 기존 아키텍처 문서는 `apps/web`과 `apps/api`를 둔 루트 모노레포를 제안하지만, 실제 개발 지시는 `frontend`와 `backend`를 분리하고 관련 폴더만 수정하도록 요구한다.
- 선택지: 문서의 `apps/*` 모노레포 구조 유지, 또는 독립된 `frontend/`와 `backend/` 프로젝트 사용.
- 결정: 독립된 `frontend/`와 `backend/` 구조를 사용한다. T00은 `backend/`만 먼저 구성한다.
- 이유: 최신 사용자 지시를 따르고 두 런타임의 코드와 의존성 경계를 명확히 유지하기 위해서다.
- 영향: 루트 통합 workspace 및 Web 연결 페이지는 이번 backend T00 범위에 포함하지 않는다. 각 프로젝트가 자체 package manager 설정과 명령을 소유하며, 배포 시 동일 HTTPS 도메인으로 라우팅한다는 ADR-009는 유지한다.
- 되돌리는 조건: 사용자가 단일 루트 workspace로 통합하도록 명시적으로 결정할 때.

### ADR-011 회원가입 직후 로그인

- 날짜: 2026-07-31
- 상태: accepted
- 문제: 기능 명세는 회원가입 성공 후 인증 쿠키를 발급하거나 로그인 화면으로 이동하는 두 방식을 허용한다.
- 선택지: 회원가입 직후 로그인, 또는 별도 로그인 요구.
- 결정: 유효한 회원가입이 완료되면 `tg_access` 쿠키를 즉시 발급해 로그인 상태로 전환한다.
- 이유: E2E-001의 회원가입 직후 `/auth/me` 확인 흐름을 단순하게 만들고 불필요한 자격 증명 재입력을 피한다.
- 영향: 회원가입과 로그인은 동일한 공개 사용자 DTO와 쿠키 정책을 사용한다. 이후 이메일 인증을 도입한다면 자동 로그인 시점을 다시 검토해야 한다.
- 되돌리는 조건: 이메일 확인 또는 추가 가입 심사가 세션 발급 전에 필수가 될 때.

### ADR-012 T02 콘텐츠 접근 경계

- 날짜: 2026-07-31
- 상태: accepted
- 문제: 질문 모델이 생기기 전 T02에서 방 콘텐츠 접근 거부를 검증할 API 형태를 명세가 고정하지 않는다.
- 선택지: 가짜 빈 질문 피드를 만들거나 권한 확인 전용 경계를 둔다.
- 결정: T02에는 `/rooms/:slug/content-access` 권한 확인 API만 두고 질문 목록 응답은 T05까지 만들지 않는다. 소개 길이는 논리 데이터 모델에 고정된 300자를 따른다.
- 이유: 존재하지 않는 질문 데이터를 성공 응답으로 가장하지 않으면서 `ROOM_ACCESS_DENIED`를 실제 HTTP 경계에서 검증하기 위해서다.
- 영향: T05에서 실제 질문 목록 API가 같은 `RoomAccessService`를 호출하도록 교체한다.
- 되돌리는 조건: T05 질문 API 계약이 확정될 때.

### ADR-013 T03 비공개 증빙 검증과 저장소 fail-closed

- 상태: 저장소 배포 부분은 2026-08-02 ADR-024로 대체됨.

- 날짜: 2026-07-31
- 상태: accepted
- 문제: 로컬 개발용 증빙 저장과 운영 S3 저장의 경계를 지키면서 MIME 위조, 공개 URL 노출, 파일/DB 불일치를 막아야 한다. 현재 운영 S3 자격 증명과 SDK는 제공되지 않았다.
- 선택지: 선언 MIME만 확인해 로컬 저장소를 모든 환경에서 사용, 즉시 S3 SDK를 추가, 또는 파일 시그니처를 검증하고 운영 환경은 S3 구현 전까지 명확히 실패.
- 결정: JPEG/PNG/PDF 선언 MIME과 magic bytes가 일치할 때만 무작위 키로 저장한다. 개발·테스트는 정적 경로에 연결되지 않은 로컬 디렉터리와 관리자 스트리밍 endpoint를 사용한다. 운영은 `STORAGE_DRIVER=s3`만 허용하며, 현재 S3 adapter는 시작 시 명시적으로 실패한다. DB insert 실패 시 저장 파일 삭제를 시도한다.
- 이유: 제공되지 않은 배포 자격 증명이나 불필요한 production dependency를 가정하지 않으면서 비공개 저장 요구를 fail-closed로 지키기 위해서다.
- 영향: 운영 배포 전 private bucket, 최소 IAM 권한, AWS SDK 기반 put/presign/delete 구현이 필요하다. API DTO에는 object key, 다운로드 URL, 파일 경로, 정확한 GPS를 포함하지 않는다.
- 되돌리는 조건: 운영 private S3 bucket과 자격 증명 주입 방식이 확정될 때 S3 adapter 내부 구현만 교체한다.

### ADR-024 T11 production 비공개 S3 스트리밍

- 날짜: 2026-08-02
- 상태: accepted
- 문제: production은 S3를 강제하지만 기존 어댑터가 시작 즉시 실패하고, 다운로드 계약도 로컬 파일 경로를 전제로 해 실제 배포가 불가능했다.
- 결정: AWS SDK v3로 안전한 prefix의 객체만 AES256 서버 암호화해 저장·조회·삭제한다. 다운로드는 공개 URL이나 object key를 클라이언트에 주지 않고 기존 API 권한 확인 뒤 서버 스트림으로 전달한다. AWS 자격 증명은 instance role 또는 표준 provider chain에서 받고 bucket과 region만 앱 시작 시 필수 검증한다.
- 이유: 로컬과 production 저장소가 같은 비공개 계약을 사용하면서 인증 증빙·채팅·토픽·답변 이미지를 동일한 권한 경계 안에 유지하기 위해서다.
- 영향: S3 bucket public access block, prefix 제한 IAM, versioning/retention/backup은 배포 인프라에서 설정해야 한다. 단위 테스트는 명령과 key 검증을 확인하지만 실제 IAM/bucket smoke는 T11 외부 완료 조건으로 남는다.
- 되돌리는 조건: 다른 private object storage로 이전하면 `StorageService`의 stream 계약을 유지한 채 adapter만 교체한다.

### ADR-014 T05 질문 커서와 동시 생성 제한

- 날짜: 2026-07-31
- 상태: accepted
- 문제: 질문 목록이 같은 생성 시각에서도 중복·누락 없이 페이지되어야 하고, 동시에 들어온 네 번째 질문이 열린 질문 3개 제한을 우회하면 안 된다.
- 선택지: id 단일 cursor와 사전 count, serializable transaction 재시도, 또는 복합 cursor와 사용자·방 단위 PostgreSQL advisory lock.
- 결정: `createdAt DESC, id DESC` 복합 Base64URL cursor를 사용하고, 생성 transaction 안에서 `pg_advisory_xact_lock(hashtext(userId || ':' || roomId))` 후 활성 OPEN 질문을 count/create한다.
- 이유: 고정 PostgreSQL 스택에서 추가 dependency나 전역 잠금 없이 페이지 안정성과 동일 사용자·방의 생성 경쟁을 작게 직렬화할 수 있다.
- 영향: cursor는 내부 구현으로 취급하고 클라이언트가 해석하지 않는다. 다른 DB로 전환하면 advisory lock 구현을 교체해야 한다.
- 되돌리는 조건: 데이터 저장소 변경 또는 범용 idempotency/분산 잠금 계층 도입 시.

### ADR-015 T06 실시간 전송과 복구 계약

- 날짜: 2026-07-31
- 상태: accepted
- 문제: REST 쓰기와 Socket 이벤트 사이에 원자적 브로커가 없고, 연결 중단 동안 이벤트가 유실될 수 있다.
- 선택지: Socket에서 쓰기 수행, DB 트랜잭션 안에서 emit, outbox/event log, 또는 커밋 후 best-effort emit과 REST 재조회.
- 결정: 모든 쓰기는 REST에서 커밋한 뒤 `RealtimePublisher`로 한 번 emit한다. 기본 namespace와 `/socket.io` path만 사용하고, 재연결 시 클라이언트가 다시 join한 후 REST 목록·상세를 재조회한다.
- 이유: 작은 MVP에서 DB를 최종 진실로 유지하고 커밋 전 유령 이벤트를 막으며, 별도 메시지 브로커 없이 연결 유실을 복구할 수 있다.
- 영향: 이벤트 발행 실패는 커밋을 롤백하지 않고 로그로 남긴다. 이벤트 `eventId`와 entity id는 UI 중복 제거에 사용하지만 이벤트 replay를 보장하지 않는다.
- 되돌리는 조건: 이벤트 전달 보장이나 다중 API 인스턴스가 필요해지면 transactional outbox와 공유 Socket adapter를 도입한다.

### ADR-016 대화 중심 방과 구조화 토픽

- 날짜: 2026-08-01
- 상태: accepted
- 문제: 질문 카드가 방 전체를 차지하면 여행자끼리 짧은 현장 정보를 공유하거나 대화에서 중요한 상황을 자연스럽게 발전시키기 어렵다.
- 선택지: 질문 스레드만 유지, 별도 자유 채팅만 추가, 또는 대화를 기본 타임라인으로 두고 기존 질문을 구조화 토픽으로 사용.
- 결정: 유효한 여행자와 현지인은 같은 방에서 실시간 메시지를 작성한다. 기존 `Question` 레코드와 답변 스레드는 UI에서 `토픽`으로 표현하며, 두 참여자 유형 모두 직접 토픽을 만들거나 본인이 작성한 메시지를 한 번 토픽으로 전환할 수 있다. 구조화 답변 작성은 이번 보완 범위에서 현지인 전용 규칙을 유지한다. 관리자는 계속 읽기 전용이다.
- 이유: 짧고 빠른 참여자 정보 공유와, 오래 남겨 답변·해결할 필요가 있는 상황을 한 화면에서 함께 제공하기 위해서다.
- 영향: 메시지는 DB와 REST가 최종 진실이며 커밋 후 Socket 이벤트를 전송한다. 콘텐츠 생성 시점의 참여자 유형을 저장해 인증 만료 후에도 공개 배지를 안정적으로 표시한다. 기존 질문 API 이름은 호환성을 위해 유지하고 프론트엔드 용어만 토픽으로 변경한다.
- 되돌리는 조건: 메시지 운영 비용이나 악용이 구조화 토픽의 효용보다 커져 자유 대화를 제거할 때.

### ADR-017 T09 단일 인스턴스 rate limit

- 날짜: 2026-08-01
- 상태: accepted
- 문제: SAFE-002의 사용자/IP 제한이 필요하지만 발표 배포는 API 한 대이고 외부 Redis·모니터링 서비스는 T09 범위 밖이다.
- 선택지: 외부 공유 저장소 도입, 프로세스 메모리 fixed window, 또는 제한 미구현.
- 결정: 로그인 IP와 토픽·답변·신고 사용자 키를 사용하는 메모리 fixed-window limiter를 적용한다. `NODE_ENV=test`에서는 공유 loopback IP로 인한 통합 스위트 상호 오염을 막고 limiter를 격리 단위 테스트한다.
- 이유: 추가 운영 의존성 없이 단일 인스턴스 발표 환경의 기본 악용을 제한하고 429/Retry-After 계약을 검증하기 위해서다.
- 영향: API 재시작 시 카운터가 초기화되고 여러 API 인스턴스 사이에는 공유되지 않는다.
- 되돌리는 조건: 수평 확장 또는 지속적인 공개 운영 시 Redis 기반 공유 limiter로 교체한다.

### ADR-018 여행지 확장형 브랜드와 일반 여행 커뮤니티

- 날짜: 2026-08-01
- 상태: accepted
- 문제: 현재 활성 방은 제주 하나지만 제주 전용 서비스처럼 보이며, 증빙 인증 전 사용자가 여행 정보를 나눌 공간이 없다.
- 선택지: 제주 인증방만 유지, 완전 익명 커뮤니티, 또는 로그인 계정 기반 일반 커뮤니티와 인증 실시간방을 병행.
- 결정: 브랜드는 여러 여행지로 확장 가능한 언어를 사용하고 제주는 첫 활성 지역으로 표현한다. 일반 커뮤니티는 로그인만 요구하며 여행자·현지인 증빙 인증 없이 게시글과 댓글을 작성할 수 있다. 익명 작성은 허용하지 않는다.
- 이유: 가입 직후 가치를 제공하면서도 작성자 책임, 신고 중복 방지, 운영 감사 가능성을 유지하기 위해서다.
- 영향: 일반 커뮤니티와 인증 실시간방은 권한과 신뢰 수준을 UI에서 명확히 구분한다. 커뮤니티 게시글·댓글도 기존 신고 및 관리자 soft removal 대상이 된다.
- 되돌리는 조건: 익명 참여의 가치가 운영 위험보다 크다는 별도 정책과 악용 방지 수단이 확정될 때.

### ADR-019 인증 방의 리치 메시지와 구조화 현장 정보

- 날짜: 2026-08-01
- 상태: accepted
- 문제: 채팅에서 토픽을 만들 수는 있지만 토픽을 다시 대화 흐름에 공유할 수 없고, 사진·장소·대기 현황처럼 텍스트만으로 부족한 현장 정보 계약이 없다.
- 선택지: 모든 첨부를 일반 JSON에 포함, 외부 지도·이미지 서비스 도입, 또는 인증 방 안에 명시적인 메시지 유형과 구조화 현장 답변 추가.
- 결정: 텍스트·보호 이미지·사용자 확인 장소·토픽 공유를 별도 메시지 유형으로 저장한다. 위치 좌표와 이미지는 유효한 방 열람 권한이 있는 사용자에게만 제공한다. 대기 현황 답변은 대기시간·혼잡도·입장 상태·관측 시각을 선택적으로 구조화하며 서버가 중앙값과 합의 상태를 계산한다.
- 이유: REST/DB를 최종 진실로 유지하면서 채팅 카드와 토픽 상세가 같은 명시적 계약을 사용하고, 현장 정보의 시점과 근거를 설명할 수 있기 때문이다.
- 영향: 위치 공유에는 별도 확인 UI가 필요하고, 이미지 객체는 DB 실패 시 정리해야 한다. 기존 텍스트 메시지와 일반 답변은 기본값/null로 호환된다.
- 되돌리는 조건: 외부 지도·미디어 플랫폼을 도입하거나 구조화 현장 데이터의 운영 비용이 정보 가치보다 커질 때.

### ADR-020 인증 참여자의 토픽 답변

- 날짜: 2026-08-01
- 상태: accepted
- 문제: 현장에 있는 인증 여행자도 대기·혼잡·운영 정보를 직접 확인할 수 있지만 기존 답변 권한은 현지인에게만 열려 있다.
- 선택지: 현지인 전용 유지, 여행자는 채팅으로만 공유, 또는 모든 유효 인증 참여자가 답변하고 배지로 정보 제공자 유형을 구분.
- 결정: 유효한 여행자와 현지인 모두 다른 사용자의 열린 토픽에 답변할 수 있다. 답변 작성 시 참여자 유형을 저장하고 `인증 여행자`, `인증 현지인`, `여행자·현지인 인증` 배지를 표시한다. 자기 토픽 답변 금지와 사용자별 답변 제한은 유지한다.
- 이유: 현장 정보의 유용성은 거주 여부뿐 아니라 현재 관찰 가능성에도 좌우되며, 출처 유형과 인증 배지를 함께 제공하면 사용자가 근거를 판단할 수 있기 때문이다.
- 영향: 기존 답변은 이전 정책에 따라 현지인 유형으로 마이그레이션하며, 현장 상태 집계에는 두 참여자 유형의 유효한 답변을 모두 포함한다. 관리자는 계속 읽기 전용이다.
- 되돌리는 조건: 여행자 답변의 신뢰도나 악용 문제가 배지 구분과 신고 정책으로 관리되지 않을 때.

### ADR-021 열린 웹앱의 브라우저 알림

- 날짜: 2026-08-01
- 상태: accepted
- 문제: 사용자가 인증 방을 열어 두고 다른 탭을 보는 동안 새 메시지와 답변을 놓칠 수 있지만, 서버 푸시 인프라는 MVP 범위 밖이다.
- 선택지: 알림 없음, 서비스 워커와 Web Push 서버 도입, 또는 현재 열린 페이지의 Socket 이벤트로 브라우저 알림 제공.
- 결정: 사용자가 방 헤더에서 명시적으로 권한을 허용하고 알림을 켠 경우에만, 보이지 않는 탭에서 다른 사용자의 메시지와 답변을 브라우저 알림으로 표시한다. 선택은 브라우저 로컬 저장소에 유지하며 페이지를 닫으면 알림도 중단된다.
- 이유: 새 backend endpoint나 푸시 자격 증명 없이 기존 실시간 계약을 활용하고, 권한 요청을 사용자 동작에 묶어 브라우저 정책과 사용자의 통제를 지키기 위해서다.
- 영향: OS·브라우저에서 거부한 권한은 앱이 다시 요청하지 않는다. 다중 기기 설정은 동기화되지 않으며 알림 전달 보장은 없다.
- 되돌리는 조건: 앱이 닫힌 상태의 알림이나 전달 보장이 필요해지면 서비스 워커, Push API, 서버 구독 모델을 별도 설계한다.

### ADR-022 토픽 현장 사진의 비공개 근거 자료화

- 날짜: 2026-08-01
- 상태: accepted
- 문제: 대기줄·휴무·혼잡 같은 토픽은 텍스트만으로 현장 상황을 설명하기 어렵지만, 사진을 공개 URL로 제공하면 인증 방의 접근 경계를 우회한다.
- 선택지: 토픽 사진 제외, 공개 정적 업로드, 또는 질문 레코드에 비공개 객체 메타데이터를 연결하고 권한 endpoint로 제공.
- 결정: 직접 생성하는 토픽에 JPEG·PNG·WebP 한 장을 선택적으로 첨부한다. 파일은 기존 비공개 저장소에 두고 방 조회 권한을 확인하는 API에서만 제공한다. 목록과 상세 응답에는 보호 endpoint와 표시용 파일명·MIME만 포함한다.
- 이유: 기존 StorageService와 RoomAccessService를 재사용해 새 의존성 없이 현장 근거를 보강하고, 메시지·답변 이미지와 동일한 보안·정리 규칙을 유지하기 위해서다.
- 영향: 사진 생성은 별도 multipart endpoint를 사용하고 기존 JSON 및 메시지 전환 API는 호환된다. 운영 숨김 후 파일 자체는 보존하지만 메타데이터 응답과 다운로드를 즉시 차단한다.
- 되돌리는 조건: 콘텐츠 보존 정책이 확정되어 관리자 숨김 시 원본 삭제가 필요하거나, 다중 사진이 제품 가치로 검증될 때 별도 미디어 모델을 설계한다.

### ADR-023 조건부 DB 전환 기반 토픽 만료

- 날짜: 2026-08-01
- 상태: accepted
- 문제: 응답에서만 만료 상태를 계산하면 DB의 OPEN 토픽이 진행 중 목록에 계속 포함되고 여러 API 인스턴스가 같은 만료를 처리할 수 있다.
- 선택지: 조회 시에만 파생 상태 유지, 외부 작업 큐·스케줄러 도입, 또는 앱 lifecycle timer와 조건부 DB 갱신 사용.
- 결정: `QuestionStatus.EXPIRED`를 영속화하고 API 시작 시 및 60초마다 최대 100건을 처리한다. 각 레코드는 `id + OPEN + expiresAt <= now` 조건의 updateMany로 경쟁을 해결하고, 성공한 인스턴스만 커밋 후 기존 질문 갱신 이벤트를 발행한다.
- 이유: 파일럿 규모에서 새 운영 의존성 없이 상태 정확도를 확보하고, 다중 인스턴스에서도 중복 이벤트를 막는 DB 최종 진실 원칙을 유지하기 위해서다.
- 영향: 프로세스가 중단된 동안의 만료는 다음 시작 시 복구된다. 주기 실행 관측성과 대량 처리량은 제한적이며 Socket 유실은 기존 reconnect refetch로 복구한다.
- 되돌리는 조건: 만료 작업량·운영 SLA가 커지거나 여러 종류의 예약 작업이 생기면 외부 스케줄러와 transactional outbox를 도입한다.

### ADR-024 점수 없는 공개 기여 이력

- 날짜: 2026-08-02
- 상태: accepted
- 문제: 답변 작성자의 신뢰 근거는 필요하지만 평점·순위·리워드는 MVP 제외 범위이며, 한 사용자가 여행자와 현지인 인증을 동시에 가질 수 있다.
- 선택지: 현지인 전용 별도 프로필, 사용자 평점, 또는 모든 답변자의 사실 기반 공개 기여 이력.
- 결정: 모든 답변자에게 공개 프로필을 제공하고 숨김되지 않은 답변 수와 공개 토픽에 채택된 답변 수만 표시한다. 현재 유효한 현지인 인증이 있으면 인증 지역과 시점을 함께 표시한다.
- 이유: 고정 계정 타입을 만들지 않으면서 사용자가 답변의 맥락을 판단할 수 있고, 제품 범위 밖의 경쟁적 점수화를 피할 수 있다.
- 영향: 수치는 요청 시 집계하며 품질 점수나 채택률로 해석하지 않는다. 이메일·증빙·GPS·심사자 정보는 선택하거나 반환하지 않는다.
- 되돌리는 조건: 활동량이 커져 조회 비용이 문제가 되면 집계 테이블 또는 캐시를 도입한다.

### ADR-025 현재 스냅샷 기반 관리자 KPI

- 날짜: 2026-08-02
- 상태: accepted
- 문제: MVP KPI는 계산 가능해야 하지만 별도 분석 플랫폼과 시계열 저장은 범위 밖이다.
- 선택지: 지표 미노출, 집계 테이블·이벤트 파이프라인, 또는 운영 화면 요청 시 PostgreSQL 원천 데이터 집계.
- 결정: 관리자 요청 시 공개 상태의 질문·답변 생성 시각과 상태를 읽어 현재 스냅샷을 계산한다. 비율은 소수점 한 자리, 최초 답변 시간은 분 단위로 반환한다.
- 이유: 별도 운영 의존성 없이 명세의 KPI를 재현 가능하게 제공하고 파일럿 데이터 규모에서 충분히 빠르기 때문이다.
- 영향: 과거 추세는 제공하지 않으며 데이터가 커지면 집계 비용이 증가한다.
- 되돌리는 조건: 운영 추세나 기간 필터가 필요해지면 집계 테이블과 예약 작업을 별도 설계한다.

### ADR-026 채팅 장소 스냅샷 기반 찜

- 날짜: 2026-08-08
- 상태: accepted
- 문제: 사용자는 인증방에서 추천받은 장소를 대화가 지나간 뒤에도 다시 찾고 싶지만, 외부 지도 공급자와 장소 ID 계약은 아직 확정되지 않았다.
- 선택지: 브라우저 로컬 저장, 지도 API 도입 후 구현, 또는 서버가 채팅 장소 스냅샷을 사용자별로 저장.
- 결정: 인증된 사용자는 열람 가능한 장소 메시지를 서버에 찜한다. 찜 레코드는 원본 메시지를 참조하면서 이름·주소·좌표 스냅샷을 보존하고, 사용자별 목록과 명시적인 저장/해제 API를 제공한다.
- 이유: 지도 공급자 선택과 무관하게 지금 가치를 제공하고, 기기 간 동기화와 소유권 검사를 서버에서 보장하기 위해서다.
- 영향: 삭제된 장소 메시지는 새로 찜할 수 없지만 이미 저장한 장소 스냅샷은 유지한다. 향후 Google Places를 연결할 때 공급자 장소 ID를 선택적으로 추가한다.
- 되돌리는 조건: 지도 공급자의 저장·표시 정책 때문에 장소 스냅샷 보존 범위를 제한해야 할 때 데이터 모델과 보존 정책을 재검토한다.

### ADR-027 Google Maps와 Places 기반 장소 선택

- 날짜: 2026-08-08
- 상태: accepted
- 문제: 좌표 직접 입력은 모바일 사용성이 낮고 장소명·주소의 정확성을 보장하지 못하며, 주변 영업 장소 탐색도 제공하지 못한다.
- 선택지: Geoapify 유지, Google 지도만 사용하고 장소는 수동 입력, 또는 Google Maps JavaScript API와 Places API (New)를 함께 사용.
- 결정: 지도 렌더링은 제한된 브라우저 키로 Google Maps JavaScript API를 사용하고, 장소 검색과 주변 영업 장소 조회는 서버의 Places API (New) 프록시를 사용한다. 선택한 Google Place ID를 장소 메시지와 찜 스냅샷에 보존한다.
- 이유: 국내외 장소 데이터와 영업시간 품질을 우선하면서 서버 키 노출을 막고, Google 요청 필드를 중앙에서 제한해 비용을 통제하기 위해서다.
- 영향: Vercel에는 브라우저 제한 키, Railway에는 Places 전용 서버 키가 필요하다. 영업시간 조회는 높은 과금 등급이므로 사용자 동작으로만 호출하고 결과 수를 제한한다.
- 되돌리는 조건: Places 비용이나 약관 제약이 제품 가치보다 커지면 공급자 중립 API 계약을 유지한 채 다른 지도 공급자로 교체한다.

### ADR-028 주변 탐색과 소유자 전용 여행 기록

- 날짜: 2026-08-09
- 상태: accepted
- 문제: 주변 영업 장소 탐색이 채팅의 장소 전송 흐름에 섞여 있고, 사용자가 자신의 여행 성향과 과거 여행을 구조화해 남길 수 없다.
- 선택지: 채팅 첨부 안에 유지, 홈 보조 링크로만 제공, 또는 반복 사용 기능인 주변 탐색을 메인 탭으로 분리하고 프로필에 여행 스타일·기록을 추가.
- 결정: 메인 내비게이션의 인증 탭을 `주변`으로 대체하고 인증 진입은 프로필에 둔다. 주변 탭은 명시적인 위치 권한 동작 이후 영업 중 식당·카페를 지도와 목록으로 보여준다. 프로필은 허용된 여행 스타일 태그를 저장하며, 여행 기록은 소유자만 조회·생성·삭제할 수 있는 목적지·기간·한줄 기록으로 저장한다.
- 이유: 인증은 설정 성격이지만 주변 탐색은 여행 중 반복 사용하므로 주 내비게이션 우선순위가 더 높다. 여행 기록을 공개 평판과 분리하면 개인정보 노출 없이 사용자의 회고 가치를 제공할 수 있다.
- 영향: 주변 조회는 사용자가 버튼을 누를 때만 위치와 Places 영업시간 API를 사용한다. 여행 기록은 공개 프로필에 포함하지 않고 정확한 GPS나 이동 경로를 저장하지 않는다.
- 되돌리는 조건: 인증 접근성이 낮아지거나 여행 기록 공개 요구가 검증되면 내비게이션과 공개 범위를 별도 결정으로 재검토한다.

### ADR-029 발표 후보의 핵심 흐름 우선순위와 관리 데모 리셋

- 날짜: 2026-08-15
- 상태: accepted
- 문제: 커뮤니티와 주변 탐색이 핵심 실시간방보다 먼저 노출되고, 데모 시드를
  반복하면 오래된 토픽 시각과 연습 메시지 또는 숨김 플레이스홀더가 발표
  타임라인에 남았다.
- 결정: 홈과 기본 내비게이션은 인증 실시간방을 선택 기능보다 먼저 표시한다.
  승인된 인증 유형은 재신청 CTA 대신 인증 현황을 표시한다. Guarded demo seed는
  네 관리 데모 참여자가 제주방에 작성한 비이미지 메시지와 관련 신고만 삭제하고,
  이미지 메시지는 객체 고아 방지를 위해 soft removal한다. 관리 대표 토픽의 과거
  답변은 숨김 처리하고, 두 현장 답변과 세 메시지 장면은 같은 실행 시각을 기준으로
  다시 생성한다. 대표 토픽 밖의 비데모 사용자 콘텐츠는 유지한다.
- 이유: 발표의 첫 화면과 데이터가 제품의 핵심 가설인 인증된 실시간 판단을 바로
  설명해야 하며, 비공개 파일 보존과 비데모 사용자 데이터 경계도 유지해야 한다.
- 영향: 커뮤니티·주변·장소 찜은 구현된 선택 기능으로 남지만 발표 핵심 흐름 뒤에
  위치한다. 데모 계정은 재시드 시 제주방 비이미지 메시지 이력이 초기화된다.
- 되돌리는 조건: 파일럿 데이터가 별도 격리 데이터베이스나 전용 데모 방으로
  이동하면 계정 기반 정리 대신 해당 격리 단위를 재생성한다.

### ADR-030 여쭈어 표시 브랜드와 기술 식별자 분리

- 날짜: 2026-08-15
- 상태: accepted
- 문제: 발표와 사용자 화면에는 기억하기 쉬운 최종 서비스명이 필요하지만, 출시 직전 저장소·배포·DB·브라우저 저장 키를 함께 바꾸면 기능과 운영 계약에 불필요한 회귀 위험이 생긴다.
- 결정: 문장과 접근성 이름에는 `여쭈어`, 영문명과 저작권에는 `Yeojju`, 시각 로고에는 `여JJU`를 사용한다. 저장소명, 패키지명, 배포 변수, DB·스토리지명, 데모 이메일 도메인, 브라우저 저장 키와 TypeScript 통합 식별자는 기존 `travelguide` 이름을 유지한다.
- 이유: 새 이름을 일관되게 전달하면서 기능과 배포 안정성을 보존하기 위해서다.
- 영향: 코드 검색에는 두 이름이 공존하며, `TravelGuide`는 사용자 문구가 아니라 내부 호환 식별자로만 남는다. 기존 발표 캡처는 필요 시 새 브랜드로 다시 생성한다.
- 되돌리는 조건: 별도 마이그레이션 계획과 배포 점검표를 마련한 뒤 기술 식별자까지 변경하기로 결정할 때 재검토한다.
